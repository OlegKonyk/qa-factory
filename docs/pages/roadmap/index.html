What the factory builds next

The QA part runs end to end on two real open-source applications and has shipped five tickets. This page lays out what comes next, in the order I recommend, and the four choices that are yours. Revised the same day after your review: where a person steps in, what Restate is for, and what the published practice of 2026 says.

Recommended: make it adoptable by a real service first. Run the generated tests against a running copy of the application, fix three gaps the last runs found, onboard a third application shaped like a small team service with a bug-fix ticket, and expose every point where a person approves or corrects. About 12 USD of model spend and four sessions, two of them cloud sessions (estimated).

Then the whole factory: an agent writes the change itself, and Ship opens a pull request instead of a local commit.

Every cost on this page is an estimate from the runs so far. Nothing on it has been built yet.

The order

The items

1Run the tests against a running application now

The second check in your scheme: develop on mocks, then the same cases run against the deployed application. Already approved on 10 October.

Builds
linkding from its own Docker image, a release that contains the feature, on this laptop through colima. One shipped feature's readable cases become a small suite that takes a base URL and creates its data through linkding's REST API with a token, never the database.
Done when
The suite runs against the container, shown by the command, the pass count and the time. What had to change from the tests inside linkding's suite, and why. The checklist of what makes a repository ready for agents, tested against what it took.
Cost
One session on the laptop, about 5 USD (estimated).

2Three factory fixes the last runs found now

Mutation
The factory skips every __init__.py, and mutmut 3.8.0 makes no mutant for most decorated functions. Both hit isso on 13 October, so its mutation check could not run. Fix both, or replace the tool for that case if it cannot be fixed.
Resume
When Verify stops at its spend cap after the checks passed, a re-run throws the passing tests away and pays a fresh test writer, about 4 USD (estimated from the bundles run). It should pick up at the readable cases.
Developers' tests
The check on the developers' own tests judges only tests the change added. It should also judge tests the change modified.
Done when
Each fix has a factory test, and isso's ticket, checked again on its shipped tests with no writer call, gets mutants for the changed code.
Cost
One cloud session, no model spend. Fits the one-time cloud credit (250 USD, until 5 November).

3A third application shaped like a small team service now

Shape
A web API service (FastAPI or similar), a src/ layout, a database run in Docker, and at least one outside HTTP service it calls. linkding and isso have none of these four; a small team service probably has all of them. Your service, or a public application with this shape chosen by the session (question 2).
Ticket
A bug fix. All five tickets so far are features, and the team asks about "a feature or a bug fix".
Mocks
The outside service is mocked inside the application's suite and real in the run against the running application, so your mock scheme meets real code. Mock machinery is built only if this run needs it.
Done when
Onboarded from the adoption guide alone, one ticket shipped, every place the guide was wrong fixed in it.
Cost
One session on the laptop, about 6 USD (estimated).

4Every person point exposed now

Added from your review. Built on the step contract every step already returns (a status, the files it made, and an optional question for a person), so the plain driver and Restate both get every gate.

Gates
One shape for every question: its kind, who answers, the question, the facts, and the answers it accepts. Frame stops when a criterion cannot be made checkable; Plan when a rule asks or the plan reports unknown patterns or risk; Review when the findings still stand after the fix round; Ship when a rule asks; Verify as today; Implement once item 5 makes it an agent's change.
Correct
An answer may carry a replacement: a clarified criterion, an edited plan, a test case to drop. A command reopens a passed step after you edit its artifact, so a correction made later runs through without a fresh ticket.
Configure
Per step, in the application's recipe or the ticket: automatic, the stronger model decides first, or a person. Replaces today's single on-or-off flag.
Tell, list, record
A notification when a run waits (this laptop, or a URL in the recipe). A command that lists every waiting run with its question. The answer names who gave it; the run report shows who answered what, when, and the note.
Done when
Every gate has a factory test, and a ticket with one deliberately vague criterion stops at Frame, is listed, is answered with the clarification, and runs through.
Cost
One cloud session to build, no model spend; one short run on the laptop to prove it, about 1 USD (estimated).

5An agent writes the change itself next

Builds
Implement becomes an agent that writes the change test-first from Frame and Plan. In parallel, a separate session writes the acceptance tests from the ticket without seeing the change (built already). They meet at the deterministic checks; failures go back to Implement a capped number of times, with the stronger model consulted before a person.
Known answer
Run it on tickets that already shipped. The developers' real commit and its tests are hidden from every session; after the change is written, the developers' tests run against the agent's code. That is a deterministic check of the agent's change, not a score.
Cost
One or two sessions to build, about 10 USD a ticket to run (estimated; nothing measured).

6Ship as a pull request, approve on it next

Builds
Ship pushes the ticket's test branch to a fork on your GitHub account and opens a pull request with the readable cases and the run report in its body. When the Ship gate asks for a person, the pull request's approval is the answer and the notification of item 4 carries its link. This is the merge gate, the one fixed human gate the published practice keeps besides the specification.
Cost
One session, little model spend (estimated).

Later, when a run shows the need

  1. Tickets from an issue tracker, with a check in Frame that sends a ticket back when it does not state the public contract: field names, values, labels, routes.
  2. Learn from each run: escalations, review findings, answers at the gates and repairs proposed as edits to the strategy rule and the prompts, by pull request.
  3. More tickets at once: a durable engine as the default (Restate, or Temporal if that is what work runs on), test selection when a suite gets slow, quarantine for flaky tests.
  4. Applications not in Python. The checks read pytest output and run mutmut.

Left off on purpose

  • Comparing writer models to lower the cost per ticket (about 5.5 USD, measured). The repository's rules forbid comparisons you did not ask for.
  • Mock machinery before a service with a real outside dependency needs it.
  • A dashboard beyond Restate's own UI, the factory's run report and the waiting-runs listing of item 4.
  • A protocol language for the process, GitHub Agent HQ, Claude Code routines, the Temporal harness: looked at on 14 October, recorded with dates, none needed for the next step.

Restate: what it is, and whether it is needed

Restate is a durable-execution engine: one server program that keeps a journal of every step a run takes. A run that crashes resumes at the step it was in. A run that waits for a person parks at no cost and wakes on one HTTP call. It stands in for the role Temporal has in your team's backbone; it was chosen for the trial on 10 October because it is one process and one install, where Temporal is several processes plus a database, and the Temporal harness your team saw is still, by its own README, "very early and experimental" at version 0.6.0 with no Claude Code integration.

What it gave, measured on 12 October: one real ticket end to end, a run killed mid-Verify that resumed at Verify, a gate that waited across restarts, a page per run. What it did not: the QA evidence (the run report covers it), a list view that shows a waiting run as "Running", and it ignores a normal stop signal. It holds about 250 lines of service code and 400 of tests, one dependency, and one more pair of processes to keep running. The plain driver gets the same result by exiting with the question and being run again.

Is it needed? Not for one ticket at a time on one laptop. It earns its keep when runs wait for people for days and there are several at once, which is exactly what item 4 creates and item 9 scales. Recommended: keep it behind its flag, build item 4 on the step contract so both engines get every gate, and pick the default engine when item 6 puts approvals on pull requests. Removing it is a one-session chore, as cheap later as now (question 4).

What the published practice says, 14 October 2026

You had never seen the earlier research: it lives only in the old lab, written on 6 to 8 October for its comparisons, and was never put in front of you. It covers how companies have a model write tests, how regressions run when agents write code, factory front-ends, deterministic test layers, and what the QA role becomes. It does not cover how a factory is run as a whole. A fresh pass on that, with every claim labelled checked, documentation only, or not verified, is docs/research/2026-10-14-factory-landscape.md. Its six points:

  1. The person sits at two fixed gates, specification and merge; every loop between is capped and automatic. Dropbox (about 1 in 12 pull requests from its agent platform; "a human makes the final judgment before any code reaches production", checked), Stripe (Slack message to reviewed pull request, about 1,300 a week, not verified), a vendor's factory guide (specification approval and merge as "the two human gates", documentation only). Here: the two gates the factory lacks.
  2. A process in prompts is not enforced; a process run as code is. A paper under review: "process encoded in prompts is flexible but unenforceable"; the same method run as a validated process gained 14 to 22 points on SWE-bench Verified (checked, the authors' numbers). A second paper: "execution grants no acceptance authority" (checked). Here: the driver and the deterministic checks are that enforcement; nothing to change.
  3. Durable execution is the common answer to a run that waits. Temporal, Restate and others journal the steps and park the wait (vendor blogs, not verified; Restate's own documentation checked). Here: nothing changed since October 8; the engine's value rises with gates, not tickets.
  4. The pull request is the approval surface; the code host is becoming the front. GitHub Agent HQ: issue to agent to draft pull request to a person's review, with organisation-wide policies and audit logs (checked). Here: item 6 is the right destination.
  5. Agent-written tests are verified by making them kill mutants, in every published account. Uber's generator validates with mutation testing (checked); an adversarial test-versus-mutant loop finds 8.56 % more faults than the best model-only method (checked, the authors' numbers). Here: the revert check plus mutmut is the published practice; the adversarial loop is a candidate for item 8.
  6. Measure delivery, not volume. Throughput up and stability down in the 2025 DORA report; experienced developers 19 % slower in one trial; ten reviewers wrote 61 % of comments on 878 agent pull requests at Microsoft (not verified here except the last, checked in the lab). Here: the person must not become the bottleneck; passing work is approved by the factory.
