qa-factory Architecture

A ticket goes in. Claude Code writes the API and browser tests, deterministic tools check that each test is not misleading, you approve a readable version, and the approved tests join the application's own suite. This page shows how it is built today and where it is fixed to one laptop, one ticket and one application, so we can place your use cases on it.

1 · The flow

Seven steps, and no stop when the checks pass

The driver runs the steps in order and hands each one the files the earlier steps wrote. Verify is the QA step and is built fully; the other steps are simple but real. The lettered badges mark the places a new use case would attach; section 8 lists them.

2 · Inside Verify

Cheapest check first, and any check can stop the run

Two Claude Code sessions do the writing: one writes the tests, one writes the readable cases. Everything between them is a deterministic tool with a fixed rule. Verify ran in 13.3 minutes on the first ticket.

3 · Proving a test is not misleading

Take the change out and the test has to fail for the right reason

The revert check builds a second copy of the application with the old source and the new tests, runs both, and sorts every failure by its cause. Only a failed assertion counts as proof. A test that fails because a name is missing proves only that the name is new.

Mutation testing on the changed function

mutmut 3.8.0 makes small edits to the function the feature touched, one at a time, and runs the tests against each. A test that fails kills the edit. On the first run, the generated API tests alone killed all {{CL_KILLED}} of {{CL_CHECKED}} edits on the changed lines and {{GEN_KILLED}} of {{CHECKED}} across the whole function. Together with the developers' tests, {{BOTH_KILLED}} of {{CHECKED}}. Scores are reported, not used as a threshold yet; the run fails only if nothing on the changed lines is killed.

4 · What gets approved

A readable case beside every test

Each test gets one Markdown case in the skeleton of your signoff plugin, linted by a copy of its cases.py. Here is the first of six, next to the test it describes.

TC-bookmarks-001: API lists bookmarks least recently modified first when sorted by modified ascending

area: bookmarks · role: user · priority: high · status: automated
tiles: bookmarks.sort.modified-ascending
Preconditions
  • The user is authenticated to the REST API with their API token
  • Three bookmarks: A added 2020-01-01, modified 2022-01-01; B added 2021-01-01, modified 2020-01-01; C added 2022-01-01, modified 2021-01-01
#ActionExpected
1Request GET /api/bookmarks/?sort=modified_ascThe results list exactly B, C, A in that order, not the default newest-added order C, B, A

The test it describes

bookmarks/tests/test_sort_by_modified_api.py
def test_list_bookmarks_sort_modified_asc(self):
    self.authenticate()
    a, b, c = self.setup_sort_fixture()

    ids = self.get_result_ids(
        reverse("linkding:bookmark-list")
        + "?sort=modified_asc"
    )

    self.assertEqual(ids, [b.id, c.id, a.id])

The fixture dates make all four orders different: newest added, oldest added, modified ascending and modified descending. That is what lets the test fail on the old code for a behavioural reason.

5 · Stop and resume

Every step leaves a record, so a run can wait for days

Each invocation of python -m factory run <ticket> walks the six steps. A step with a passing record is skipped. A step that needs a person writes question.md and the run exits with code 2. Your answer.json is handed to that step on the next run and then moved aside, so it can never answer a later question.

A failed step is re-run on the next invocation with its round number raised, and the old record is kept beside the new one. Since 10 October Verify approves on its own when every check passes, so a new ticket runs all six steps in one invocation; the question file is written only for a ticket that sets gate: person.

6 · Where it lives

One laptop, three places on disk, two services outside

The repository holds the code and the record. The run folders hold what a resume needs and nothing else. The cache holds the application, its environment, and one pair of worktrees per ticket, so a parked run keeps its trees while another ticket runs.

12 · Restate

A crash-safe run and a page per run; the QA evidence stays in our own report

13 · The feature loop

Not the same session: two fresh sessions in parallel, joined by the checks

Recommendation: once Frame and Plan have fixed the acceptance criteria and the public contract (parameter names, labels, routes), start two sessions at once. One writes the change and its unit tests, test-first. The other writes the acceptance tests from the criteria without seeing the code. They join on the deterministic checks. A short coverage pass then targets what the new code does that no test catches. After merge, the same cases run against the deployed environment.

Measured on 10 October: the acceptance lane, written blind

Track 1 ran the factory's new blind mode. The test writer works in the code before the change, with the ticket and the strategy rule only; every other copy of the code and git are hidden from its session, and its tool calls are audited. Its tests then meet the developers' real commit and every check runs unchanged.

Yes, QA can start when the ticket is ready, if the ticket states the public contract. On both tickets every blind test passed with the real change: no contract mismatch. On the sort ticket the blind tests were exactly as strong as tests written after the change; on the bundles ticket they killed every mutant on the changed lines.

What makes a repository agent-friendly for this loop

Drawn from the sources and from what the first run needed. Item 5 is the one linkding fails today.

  1. One documented command to build and start the app with seeded data, in the repository's agent file.
  2. Test helpers named in a strategy rule, so the factory and its checks know them. The first run needed this.
  3. A strategy rule: which kind of test goes to which level.
  4. Selectors by role and label first, test ids where roles are not enough.
  5. Test data created through the public API, not the database, for every test that must also run against a deployed environment.
  6. A base URL, test accounts and cleanup for each environment.
  7. Lint, the suite and mutation on changed code runnable locally in minutes.
  8. Logs an agent can read when a test fails.

15 · Yours to decide

Two questions

  1. Will tickets at work state the public contract (field names, values, labels, routes) before coding starts? If not, Plan has to fix it first, or the blind lane will meet mismatches the two tickets here did not have.
  2. Make Restate the default engine now, or keep it behind the flag through track 3? Recommended: keep it behind the flag and decide after track 3. The plain driver is simpler, and Restate's gains only matter once runs are long or many.
