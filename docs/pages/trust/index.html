QA factory · the question from the team

Can we trust tests written in the session that implemented the change?

The factory's answer, from four tickets run on one real open-source application between 8 and 12 October 2026 and one on a second application on 13 October. Every number on this page was measured on those runs. The limits are at the end.

No, and the factory does not try to. A test written in the same session as the change was written to pass against the code as it was just written. It shares the change's blind spots.

Measured: on the sort feature, the developers' own tests, written with the code, fail on the code before the change only because a name is missing, not because the order is wrong. They prove the code is new. They do not prove what it does.

Trust comes from somewhere else: a separate session writes the acceptance tests, and deterministic tools decide whether those tests prove anything.

What the factory does instead

  1. A different session writes the acceptance tests. A fresh headless Claude Code session with its own prompt and budget and no memory of the implementation. In blind mode it works in a copy of the code before the change; the change, every other copy of the code and git are hidden from it, and its transcript is audited afterwards for any attempt to look.
  2. The revert check. Every new test runs twice: with the change, and with the change taken out (source files and test helpers put back to their old version). A test counts only if it passes with the change and fails without it on an assertion. A test that fails without the change on a missing import, attribute or name is rejected.
  3. Mutation testing with mutmut 3.8.0 on the functions the change touched: the generated tests alone, with the developers' tests added, and the developers' tests alone. A set that kills no mutant on the changed lines fails.
  4. Lint of the generated tests: ruff, no test without an assertion, no sleeps, no mocking of the application's own code. Then the application's whole suite with the new tests in place.
  5. A readable test case per automated test, in a fixed skeleton a linter checks, committed beside the tests. The test is the proof; the case is what a product owner reads.

When a check fails, nobody is asked first: one repair round in a fresh session, then a stronger model decides retry, the change is wrong, or an environment problem. A person is asked only when it cannot decide. Rounds and spend are capped per ticket.

  • A guard is a test that passes on both versions (the fallback for an unknown sort value). It is reported, not counted as proof.
  • On the sort ticket, blind tests were exactly as strong as tests written with the change in view: 27 of 108 mutants over the whole function and 10 of 10 on the changed lines, both ways.
  • The developers' own tests on the same functions: 98 of 108 and 77 of 82 over the whole function. They cover code that was already there; on the changed lines they tie with the generated tests.
  • Every blind writer's transcript was audited: 39, 24 and 24 tool calls, none touching the hidden code or git.
  • What went wrong in four runs was the factory's own checks, not the tests. Each is fixed and recorded.

Where the answer stops

  • One application, four runs, two of them the same ticket. Blind writers vary: 13 tests and then 7 on the same ticket, both killing every mutant on the changed lines, 78 % and 62 % over the whole function.
  • Both blind tickets stated the public contract (routes, fields, values, labels) because they were written from finished commits. A ticket written before the code may not; then the plan step has to fix the contract first. Unmeasured.
  • No bug-fix ticket has run. Mutation scores are reported, not thresholded. Mutation has a blind spot of its own: mutmut 3.8.0 makes no mutant for most decorated functions, and code in __init__.py is skipped. On the isso ticket every changed function was one of those, so the revert check was the only proof; the report says so rather than pretending a score.
  • The factory today needs the finished commit. Blind means the writer did not see the change, not that it ran at the same time.
  • Approval is a file, Ship is a local commit. Nothing has run against a deployed environment.

The scenarios raised

Tests in the implementing session

Keep them as the developer's unit tests and let the checks judge them like any other test. Today the revert check judges only the generated tests; mutation testing reports the developers' tests as their own set. Running the revert check on the developers' tests too is a small change and answers "do their tests prove the behaviour" per ticket. not built

Develop on mocks, validate on the deployed environment

Read as two verification points for one set of acceptance tests.

  1. In the service's own suite, dependencies mocked the way the suite already mocks them. The revert check, mutation testing and the suite run here. This is what makes the tests trustworthy at this point. built · measured
  2. The same cases against the deployed environment, real dependencies, reached by a base URL, data created through the public API. not built The tests from point 1 can only run here if they create data through the API, not the database.

Keeping mocks reliable is a problem the factory has not touched: what a mock is kept from (a recorded exchange, the dependency's interface document, its own test double) and what checks it against the real service. Recommendation: wait for the first service with real dependencies, see how its suite mocks them, and add the check that run shows is missing.

Acceptance criteria as verification points

Already the shape. The framing step restates every criterion as something a test can check and names its surface (API, browser, unit, none), and lists what a writer would have to guess. The ticket carries the public contract as a field. A criterion the factory cannot test is reported back on the ticket. built · measured

Four lines for the meeting

  1. Tests from the implementing session prove the code is new, not what it does. Measured.
  2. Trust comes from a separate session plus deterministic checks: fails without the change on an assertion, kills mutants on the changed lines, the suite stays green, a readable case per test.
  3. On four runs the blind tests met the real change with no mismatch and were as strong as tests written with the change in view. Limits: one application, four runs, contracts stated.
  4. The deployed-environment run and anything about mocks are not built. The adoption guide says what is ready and what a service needs to use it.
